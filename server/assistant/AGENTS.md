# Purpose

The one agent: model orchestration for chat, forwarded email and pasted text through model, source and persistence interfaces.

# Ownership

Model contract, the single instruction set (`rules`, `sourceRules`, `lookupRule`), context building, the tool loop, review validation and request cost accounting.

# Local Contracts

No HTTP client or provider SDK belongs here. Model implementations live in adapters. `Run(ctx, turn)` is the only model entry. It stores nothing and applies nothing: it returns a `domain.AgentOutcome` that `command.CommitAgentTurn` stores. There is no extraction persona, no extraction-only request and no email keyword router; chat, arrival and review-reply turns share one instruction set, one context builder and one loop.
An optional model method, `RecordDiagnostic(context.Context, string, any)`, receives review rejection details and the final turn outcome or error. The model adapter owns private storage, expiry and failure handling; these diagnostics do not alter agent decisions or persistence. The recorded outcome precedes `CommitAgentTurn`; normal conversation logs report commit success or failure.
Context (`buildContext`): the instructions with lists, profiles, at most 200 open items and the open reviews (source ID, kind, label, revision, candidates; at most 10, so a review stays reachable after its card leaves history), the last 20 chat entries before the turn's own message, then the turn record. A long earlier owner message (over 4,000 bytes) shows as a `read_source` reference. An `owner` turn ends with the owner's message, whole. A `source_arrival` turn ends with an arrival record (data: source ID, revision, subject and sender as untrusted text; never an owner command). A `review_reply` turn adds a review-context record (source, candidate, revision) before the owner's words; that context never changes a candidate by itself. A request may carry up to 450,000 bytes of text (the 400,000-byte source budget plus instructions); image data is not counted. Over that, the turn fails with an `Invalid` error before the model call. There is no call cap: the request budget, the turn timeout and the monthly limit end a runaway loop, and every call is reserved, settled and billed.
Tool loop: read tools (`find_sources`, `read_source`, `inspect_review`, `find_finished_items`) return data to the same loop as tool results with the call's ID; other calls in that reply get a `Not run` result. Every tool call is answered. Source content arrives only in tool results marked as untrusted data (images follow in one user message); `read_source` records the document so evidence can be checked. Missing, deleted or unreadable sources come back as tool results, never invented. Storage and cancellation errors end the turn. `list_items` ends the turn with the list as text. `offer_lookup` stands alone; the model may offer again after results.
`propose_review` is checked before it ends the turn, and problems go back to the model as a tool result so it can fix them: one call per reply; a known source; the review's expected revision (0 for pasted text with no review); each updated candidate exists, is not confirmed or discarded and quotes its current revision; actions are create, update, cancel or complete; each new candidate has evidence that is a literal contiguous quote from a part of a source read in this turn. Quote checking is mechanical and claims no semantic support. Options are capped at three, duration questions without options get 30 minutes, 45 minutes and 1 hour, and only allowed reminder offsets stay. A review sends only new candidates and the ones it changes; omitted candidates are untouched.
The instructions separate source facts, owner answers and assumptions. An end time or duration needs source or owner support; a start with no length asks how long and leaves end and duration empty. When asked where a value came from, the agent reads the source and says plainly whether it supports it. The model writes the English opening (`summary`) and push line (`notification`); the server keeps their text. Online meetings have no address: the prompt tells the model to leave `location` empty; code never judges a location. Chat tools are `propose_create`, `propose_update`, `propose_complete`, `propose_cancel` (status `cancelled`), `propose_delete` (removes the item and its data), `propose_profile`, `list_items` and `find_finished_items` (`query`, `list`: matches of done and cancelled items, newest first, at most 50, as untrusted data).
The prompt asks the model to propose required preparation and follow-up actions as separate task candidates, including one questionnaire task for several visits. A deadline does not settle when to do the task: ask for a timing choice before the earliest relevant appointment unless the owner already chose. Offer useful future choices such as one day, two days or a week before, adapting to earlier source deadlines and the available time. Keep suggestions separate from source facts. A timing answer schedules the task with start_at, retains the source deadline separately and sets one remind_at for the work time with offsets cleared; it does not merely move a notification. Explicit notification-only changes preserve the task date. Update only the answered task. These decisions stay in the model; add no keyword routing or timing parser to production code.
Keep at most 200 open items in context. Reserve cost before calling the model; settle known costs and keep reservations for unknown ones. Usage details carry the turn kind and, for source turns, the source ID. The outcome carries the summed cost; commit puts it on the first entry only.
Lookups are optional (`WithLookups`). With a finder set, `Message.Purpose` on the first message is `PurposeOffer`, the prompt gains `lookupRule` and the model may call `offer_lookup` (`kind`: maps, places or search; `query`) alone. The server stores only the fixed-format offer entry (`domain.OfferText`); an unknown kind or blank query is an error. The offer is the owner's approval of that exact search. Only when the owner's text is `Look it up` and the newest entry before it is an offer (error entries and earlier Look it up messages are skipped, so Retry works) does the server run that kind and query through the `Finder` and add the hits to the request as untrusted data (at most three hits). A failed or empty search says so. Any other text, a stale offer or a missing finder runs no search. Logs carry `kind` and `query_len`, never the query.
Sources are optional (`WithSources`): a `SourceReader` with `FindSources` and `ReadSource`, implemented by `capture.Service`. Without one the source tools answer that sources are unavailable.

The prompt tells the agent that a task without a start or deadline appears on the owner's Board (To pick up, In progress, Done), not to invent a due date for it, to use `propose_update` with `status` `in_progress` when the owner starts or works on a task (not `list_items`) and `open` when they pause or reopen one, and to take `item_id` and `expected_version` only from Current items. Real-model runs showed the agent otherwise copying a change ID from chat history as an item ID.
